从零手写一个 Agent 的学习路径 · 纯 Go · 本地大模型

1. 这是什么 / 为什么要做

纯 Go本地模型教学导向

市面上的 Agent 框架太多 (LangChain / LlamaIndex / AutoGen...), 每一个都有一堆概念要学. 本项目反其道而行 — 自己手写一个.

目标不是替代框架, 而是:

  • 看见每一根线: 从 HTTP 调用到 SSE 流式, 一行一行自己写.
  • 用统一业务场景 (台湾电商文案) 贯穿所有里程碑, 不切换上下文.
  • 不依赖云端 API — 没有 GPU 也能用 fake server 跑通流程.

2. 分层架构

Agent 拆成 4 个水平层：入口 → 应用 → 领域 → 基础设施。上层调用下层提供的能力，不反向依赖。下面每一层的职责和对应的 Go 文件：

说明：分层架构的意义是让"业务会不会写文案"和"网络怎么连接模型"两个问题解耦。将来要换模型、换浏览器 UI 时，只改最底层或最上层，不需要动中间的领域层。

2.1 一条用户消息的数据流

用户在浏览器里输入一句话，点击"发送"后，这条消息会依次经过以下 5 个"处理节点"，最终以字符流的形式回到浏览器。每个节点对应一段可单独打开看的源码文件。

① 浏览器HTML + JS
chat.js 发 fetch
→
② chat API handlerinternal/web/handlers_chat.go
POST /api/chat
→
③ 会话记忆internal/memory/shortterm.go
Append + EnsureBudget
→
④ LLM 协议internal/llm/client.go
ChatStream (OpenAI 兼容)
→
⑤ 真正的模型llama.cpp / Ollama / fake-openai
POST /v1/chat/completions

回复的路径是反向的：⑤ 把 data: {"content":"..."}\n\n 的 SSE 帧流式吐给 ④ → ④ 写回给 ② 的 http.Flusher → ② 原样转发给浏览器 → 浏览器 chat.js 拼接并显示。

2.2 一次完整调用链（6 步）

1

用户输入 → HTTP POST /api/chat

浏览器发起 JSON 请求：{"conversation_id":"...","message":"写文案..."}。如果是首次发送，conversation_id 为空，服务端会新建一个。

2

handlers_chat.go · handleChatAPI()

定位到 ConversationStore，把用户消息写入该会话的 ShortTerm（即 memory 里的消息历史）。如果上下文已超出 token 预算，这里会触发滑窗 / 摘要。

3

memory.Snapshot() → 构造 messages 数组

把 [system, user, assistant, user, assistant, ...] 拼成 OpenAI 协议要求的 JSON 数组。system 来自角色卡，每轮 user/assistant 来自历史消息。

4

llm.OpenAIClient.ChatStream()

向 OPENAI_BASE_URL 发起 POST /v1/chat/completions，请求里带 stream=true，模型会以 text/event-stream 形式一块一块返回。

5

handlers_chat.go · writeSSE()

收到的每一段 content delta，立刻转成浏览器认识的 SSE 帧：event: delta\ndata: {"content":"..."}\n\n，并调用 http.Flusher.Flush() 立刻写回 TCP 连接。这一步让字一个一个出现。

6

chat.js onmessage → 拼接并渲染

浏览器端监听 event: delta，把每次 content 追加到一个字符串，再塞进气泡 div 的 innerText。流式结束时收到 event: done，聊天条标记完成。

4. M0 · 最小骨架

M0 要做的事非常简单: 发一条消息给 LLM, 流式收到回复. 但 "简单" 背后有三个设计决策值得理解, 它们会影响后续所有里程碑.

设计决策 1: 为什么用 OpenAI 兼容协议?

市面上的本地推理后端 (llama.cpp / Ollama / vLLM) 都暴露了 同一套 HTTP 接口: POST /v1/chat/completions. 只要我们按这个协议发请求, 就能:

  • 换后端零成本: 今天用 llama.cpp, 明天换 Ollama, 代码一行不改
  • 测试零依赖: 写一个 fake server 模拟这个协议, 不下载任何模型也能跑通全流程
  • 未来可切云: 想用 OpenAI/Claude API? 同一个 Client, 换个 base_url 即可

反例: 如果自己设计协议, 每换一个后端就要写一层 adapter, 教学项目会陷入胶水代码.

设计决策 2: 为什么用 interface 而不是直接调 HTTP?

Client 是一个 interface, 只有两个方法. 测试时可以注入 fake, 生产时注入真实 HTTP client. 这是 Go 的惯用做法, 但更重要的是: 它让 "调 LLM" 和 "怎么调 LLM" 彻底解耦.

// llm/client.go — 只有两方法的极简接口
type Client interface {
    Chat(ctx, req) (ChatResponse, error)         // 非流式: 等完整回复
    ChatStream(ctx, req) (<-chan StreamChunk, error) // 流式: 逐字返回
}

后续里程碑 (M10 模型路由) 只需实现这个 interface, 就能在不改动任何 agent 代码的前提下, 让 "调哪个模型" 变成运行时决策.

设计决策 3: 为什么用 SSE 流式?

用户发一句话, 模型可能要推理 5-10 秒. 如果用非流式 (等完整回复再返回), 用户体验是 "转圈 8 秒 → 突然出现一大段文字". 用流式 (SSE / Server-Sent Events), 模型每生成一个 token 就推一次, 用户看到的是 "字一个一个蹦出来".

// SSE 流式原理 (3 层流式穿透)
浏览器 ←SSE←  web handler  ←HTTP stream←  LLM server
  │              │                │
  │ fetch()      │ http.Flusher   │ stream=true
  │ onmessage    │ 逐帧 flush     │ data: {"content":"你"}\n\n
  ▼              ▼                ▼
chat.js 拼接    writeSSE()      OpenAI 协议

关键: 每收到一个 delta, 立刻 flusher.Flush() 写回 TCP, 不缓冲. 这就是 "打字机效果" 的实现原理.

核心数据结构

// Message 的 role 字段决定了消息在对话中的角色
type Message struct {
    Role    Role   `json:"role"`    // system / user / assistant / tool
    Content string `json:"content"`
}
// system:    "你是一个文案专家" — 设定人设, 放在 messages[0]
// user:      "帮我写标题"       — 用户输入
// assistant: "好的, 标题是..."  — 模型回复
// tool:      '{"price": 299}'   — 工具返回结果 (M2+)

启动方式 (Fake Server + Web)

# 终端 A: 启动 fake LLM server (不需要真实模型)
go run ./agent-lab/scripts/fake-openai

# 终端 B: 启动 Web UI
set OPENAI_BASE_URL=http://127.0.0.1:18080/v1
set OPENAI_API_KEY=sk-local
set AGENTLAB_PROFILE=L
go run ./agent-lab/cmd/web
# 浏览器打开 http://127.0.0.1:8090

常见陷阱

  • SSE 不 flush: 忘记调 flusher.Flush() → 浏览器等很久才一次性收到全部, 失去流式效果
  • base_url 末尾: /v1 不能少, fake-openai 监听的是 http://127.0.0.1:18080/v1, 不是 :18080
  • API Key: 本地后端不校验 key, 但协议要求传, 所以用占位符 sk-local

5. M1 · 多轮对话

M1 解决一个根本问题: LLM 本身是无状态的. 每次 API 调用都是独立的, 模型不记得上一轮说了什么. 要让对话 "连续", 我们必须自己维护消息历史, 每次把完整历史发给模型.

为什么 LLM 是无状态的?

LLM 的推理过程是: 输入一段文本 → 输出一段文本. 模型权重在推理时不更新, 也没有 "会话" 概念. 所谓 "多轮对话", 其实是每次调用都把 之前的所有消息 重新发一遍:

第 1 轮: 发 [system, user1]              → 模型回 assistant1
第 2 轮: 发 [system, user1, assistant1, user2]  → 模型回 assistant2
第 3 轮: 发 [system, user1, assistant1, user2, assistant2, user3] → ...
         ↑ 历史越来越长, token 越来越多!

这意味着: 对话越长, 每次请求的 token 越多, 推理越慢, 成本越高 (云端按 token 计费). 所以必须有 "预算管理".

短期记忆的本质

ShortTerm 就是一个消息列表加上 token 预算管理. 它的 Snapshot() 返回 [system, user1, assistant1, user2, ...], 直接作为 LLM 请求的 messages 字段.

// memory/shortterm.go 的核心结构
type ShortTerm struct {
    system  string         // system prompt (角色卡)
    msgs    []Message      // [user, assistant, user, assistant, ...]
    budget  int            // token 预算 (如 4096)
}
func (m *ShortTerm) Snapshot() []Message {
    return append([]Message{{Role: "system", Content: m.system}}, m.msgs...)
}

token 预估: 为什么不精确?

真正的 token 数需要用 tokenizer (如 tiktoken) 精确切分. 但为了零依赖, 我们用经验公式估算:

中文: 1.5 字 ≈ 1 token   (因为中文一个字通常编码为 1-2 个 token)
英文: 4 字符 ≈ 1 token   (因为英文用 BPE, 常见词组会合并)
混合: 按字符类型分别估算后相加

这个估算偏差约 ±20%, 对 "是否需要压缩" 的判断够用. 真正的 token 数由模型返回的 usage.prompt_tokens 给出.

两步压缩策略: 滑窗 → 摘要

当历史消息的 token 超出预算时, EnsureBudget() 分两步压缩:

1

滑窗 (Sliding Window)

丢弃最早的消息, 只保留最近的 N 条. 优点: 零延迟, 无需调 LLM. 缺点: 丢失早期上下文, 模型可能 "忘记" 用户说过的重要信息.

2

摘要 (Summarization)

如果滑窗后仍超预算, 把被丢弃的消息发给 LLM: "请把以下对话摘要成一段话". 摘要结果作为一条 assistant 消息放回历史. 优点: 保留关键信息. 缺点: 多一次 LLM 调用, 有延迟.

// EnsureBudget 的伪代码
func (m *ShortTerm) EnsureBudget(ctx, client, model, budget) {
    if m.estimateTokens() <= budget { return }  // 没超, 不用管

    // 第 1 步: 滑窗 — 丢掉最旧的几条
    m.msgs = m.msgs[len(m.msgs)/4:]  // 保留后 3/4

    if m.estimateTokens() <= budget { return }  // 够了

    // 第 2 步: 摘要 — 把旧消息压缩成一条
    summary = client.Chat("请摘要以下对话: " + oldMsgs)
    m.msgs = append([]Message{{assistant, summary}}, m.msgs[recent:]...)
}

角色卡 (system prompt): 为什么保存后下条消息才生效?

system prompt 是 messages[0], 设定 agent 的人设. 用户修改角色卡后, 不重写已有消息, 只更新 ShortTerm.system 字段. 下一次 Snapshot() 时, 新的 system 会自动拼到最前面.

如果重写历史消息, 会破坏对话的因果链 — 模型会困惑 "为什么我说过的话变了". 所以 "保存后下条消息生效" 是最安全的设计.

关键调用流

1. 用户输入 → memory.Append(user, 输入)
2. memory.EnsureBudget(ctx, client, model, maxTokens)  // 检查 & 压缩
3. msgs := memory.Snapshot()  // [system, ...history]
4. client.ChatStream(ctx, {Model: model, Messages: msgs})
5. 收集流式回复 → memory.Append(assistant, 完整回复)

Web UI 的改变

  • 左侧新增"会话列表", 新建 / 切换 / 重命名 / 删除
  • 顶部角色卡编辑区, 保存后下一条消息生效 (不重写历史)
  • 服务端压缩时, UI 在消息流中插入一行灰色提示: "摘要: 压缩 N 轮 → M tokens"
  • 底部按钮: Reset / Export / Import

6. M2 · 原生 Tool Calling

M2 让模型 自己决定要不要调工具. 在此之前, Agent 只能 "说" 不能 "做" — 它不能查库存、不能算价格、不能检查合规. M2 之后, Agent 有了 "手".

为什么 LLM 需要工具?

LLM 的知识有两个硬限制:

  • 训练截止: 模型的知识停在训练数据的时间点, 不知道 "今天" 的库存和价格
  • 不能计算: 模型是 "下一个 token 预测器", 算 299 * 0.8 可能出错, 但 price_format 工具用 Go 代码算 100% 正确

工具的本质是: 让 LLM 负责决策 (何时调什么), 让传统代码负责执行 (确定性逻辑). 两者各取所长.

OpenAI Tool Calling 协议详解

协议分两半 — 请求里告诉模型 "有哪些工具可用", 响应里模型告诉你 "我想调哪个".

// 1. 请求: 在 tools 字段里声明工具的 JSON Schema
{
  "model": "qwen2.5-7b",
  "messages": [{"role":"user","content":"sku_001 多少钱?"}],
  "tools": [{
    "type": "function",
    "function": {
      "name": "product_lookup",
      "description": "查询商品信息 (名称/价格/库存)",
      "parameters": {
        "type": "object",
        "properties": {
          "sku_id": {"type":"string","description":"商品 SKU 编号"}
        },
        "required": ["sku_id"]
      }
    }
  }]
}

// 2. 响应: 模型决定调用工具时, tool_calls 字段非空
{
  "role": "assistant",
  "tool_calls": [{
    "id": "call_abc123",
    "function": {
      "name": "product_lookup",
      "arguments": "{\"sku_id\":\"sku_001\"}"  // 注意: 是 JSON 字符串
    }
  }]
}

模型看到 description 后, 会理解 "这个工具能干什么, 什么时候该用". 写好 description 是工具设计的核心.

Loop 机制: 为什么是循环?

一次工具调用不够 — 模型可能调完 product_lookup 后, 还想调 price_format 格式化价格, 再调 platform_lint 检查合规. 所以工具调用是一个 循环:

// Loop 的核心循环 (最多 MaxSteps 轮, 防无限循环)
for step := 0; step < maxSteps; step++ {
    resp = client.Chat(ctx, req)           // 1. 问 LLM (带 tools + 历史)
    if len(resp.ToolCalls) == 0 { break }   // 2. 没有工具调用 → 模型给了最终回复, 结束
    for _, tc := range resp.ToolCalls {     // 3. 执行每个工具调用
        out = registry.Get(tc.Name).Invoke(ctx, tc.Args)
        messages = append(messages, toolResult(out))  // 4. 把结果作为 tool 消息喂回
    }
    // 5. 循环回到第 1 步, 模型看到了工具结果, 决定继续调工具还是回复
}

MaxSteps (默认 8) 是安全阀 — 如果模型陷入 "调工具 → 看结果 → 再调工具" 的死循环, 到了上限就强制停止.

工具设计三原则

  • Description 面向模型: 不要写 "查商品" (太模糊), 要写 "查询商品信息 (名称/价格/库存/品牌). 输入 SKU 编号, 返回 JSON." — 模型靠这段文字判断何时该用
  • 返回值结构化: 返回 JSON 字符串 {"name":"毛巾","price":299,"stock":50}, 不要返回自然语言 — 模型需要解析结果来决定下一步
  • 参数尽量少: 一个工具 3 个参数比 10 个参数好. 参数越多, 模型越容易填错

7. M3 · 手写 ReAct

不是所有模型都支持 tool_calls 字段 (比如老模型、小模型). M3 手写 ReAct (Reason + Act) 协议 — 用纯文本让模型输出 "思考 → 行动 → 观察" 的 JSON, 不依赖协议层支持.

ReAct 的思想

2022 年 Yao 等人提出: 让模型 先推理再行动. 每一步输出三样东西:

Thought:  "用户问 sku_001 的价格, 我需要先查商品信息"
Action:   "product_lookup"
Args:     {"sku_id": "sku_001"}

→ 我们执行工具, 返回结果 →

Observation: '{"name":"毛巾","price":299,"stock":50}'

Thought:  "价格是 299, 用户可能想知道折扣价, 我格式化一下"
Action:   "price_format"
Args:     {"price": 299, "discount": 0.8}

→ 执行 →

Observation: '{"formatted":"NT$239","original":"NT$299"}'

Thought:  "我有全部信息了, 可以回复用户了"
Action:   "finish"  // 特殊 action, 表示结束

关键区别: native (M2) 靠协议层的 tool_calls 字段, ReAct (M3) 靠 prompt 工程让模型在 content 里输出 JSON. 前者更准确, 后者兼容性更好.

为什么需要容错 JSON 解析?

模型不是机器 — 它经常在 JSON 前后加废话:

模型输出 (理想):  {"thought":"...","action":"product_lookup","args":{"sku_id":"001"}}
模型输出 (现实):  好的, 我来查一下商品信息。
                   ```json
                   {"thought":"需要查商品","action":"product_lookup","args":{"sku_id":"001"}}
                   ```
                   希望能帮到你!

所以我们写了 三层容错提取:

  • extractFenced: 先找 ```json ... ``` 代码块
  • extractFirstBracePair: 再找第一个 { ... } 大括号对 (用深度计数)
  • 直接 json.Unmarshal: 如果输出本身就是裸 JSON

三种策略依次尝试, 命中即停. 这套容错逻辑在 M7 (Multi-Agent) 和 M9 (Judge) 中反复复用.

native vs react: 本质对比

native (M2)react (M3)
工具声明请求的 tools 字段system prompt 里文字描述
工具调用响应的 tool_calls 字段content 里的 JSON
准确性高 (协议保证)中 (依赖 prompt + 解析)
兼容性需模型支持任何模型
思维链无 (直接输出 tool_calls)有 (Thought 字段可观测)

8. M4 · 记忆 (短期摘要 + 长期 KV)

M1 的短期记忆只在一个会话内有效 — 新建会话就丢了. M4 加了一层 长期记忆: Agent 能记住 "卖家 A001 喜欢亲切语气", 跨会话不丢失.

两层记忆架构

短期记忆 (M1)长期记忆 (M4)
存储内存 (消息列表)SQLite (KV 表)
生命周期一个会话跨会话, 永久
内容完整对话历史结构化偏好 (tone/keywords/audience)
管理自动滑窗/摘要Agent 自主写入, 人类可遗忘
工具无 (内部管理)memory_put / memory_get
// 架构: 短期记忆在上下文里, 长期记忆在工具里

用户: "帮我写毛巾标题, 风格亲切一点"
  │
  ├─ Agent 调 memory_get(seller:A001, "tone")  → "亲切活泼, 多用 emoji"
  │   (从长期记忆取出偏好, 注入上下文)
  │
  ├─ Agent 生成文案 (带上 tone 偏好)
  │
  └─ Agent 调 memory_put(seller:A001, "last_sku", "sku_001")
      (把本次操作写入长期记忆, 下次可用)

KV 模型: namespace + key → value

长期记忆用最简单的 KV 结构, 但加了一个 namespace 维度来实现隔离:

namespace=seller:A001, key=tone,       value="亲切活泼, 多用 emoji"
namespace=seller:A001, key=keywords,   value=["現貨","免運","下殺"]
namespace=seller:A001, key=audience,   value="小资女, 25-35岁"
namespace=seller:A002, key=tone,       value="专业简洁, 突出规格"
                                       ↑ 不同卖家, 同一个 key, 值不同

为什么不用关系型表 (如 seller_profiles)? 因为 Agent 写入的记忆是 非结构化的 — 它可能今天写 tone, 明天写 favorite_color, 后天写 banned_words. KV 灵活适应任意 key, 不需要改表结构.

记忆的写入时机: Agent 自主决定

我们不硬编码 "每 3 轮写一次记忆", 而是给 Agent memory_put 工具, 让它自己判断:

  • 用户说 "我以后都要用繁体" → Agent 调 memory_put(seller:A001, "language", "繁体中文")
  • 用户说 "不要用极限词" → Agent 调 memory_put(seller:A001, "banned_words", ["最便宜","最低價"])
  • 用户只是闲聊 → Agent 不调 memory_put, 不浪费

这是 "Agentic" 的核心: 把决策权交给 LLM, 而不是用规则硬编码. Agent 可能判断错 (该记的没记), 但随着模型能力提升, 这个问题会自然缓解.

9. M5 · RAG (向量检索)

M5 让 Agent 能查 知识库 — 平台规则、商品手册、运营指南等. 关键不是 "能不能查", 而是 "怎么查": 不是关键词匹配, 而是 语义检索.

为什么不直接把文档塞进 prompt?

蝦皮台湾的运营规则可能有 50 页, 全塞进 prompt = 2 万 token, 每次 API 调用都要付这个成本. 而且 LLM 对长文本有 "中间遗忘" 问题 — 中间的信息容易被忽略.

RAG (Retrieval-Augmented Generation) 的思路: 只检索相关片段, 塞进 prompt. 用户问 "标题字数限制", 只检索到 "蝦皮标题最多 120 字" 这一段, 5 个 token 搞定.

Embedding 原理: 文本转向量

Embedding 模型把任意文本变成一个固定维度的浮点数向量 (如 128 维). 语义相近的文本, 向量也相近:

"蝦皮標題字數限制"     → [0.12, -0.34, 0.56, ...]  (128 维)
"標題最多幾個字"       → [0.11, -0.33, 0.55, ...]  ← 语义相近, 向量相近
"毛巾的材質是什麼"     → [-0.45, 0.78, -0.12, ...] ← 语义不同, 向量差异大

这个向量由 embedding 模型 (如 bge-small-zh) 生成, 它在训练时学习了 "哪些文本语义相近". 我们不需要理解向量里每个数字的含义, 只需要比较向量间的 距离.

余弦相似度: 为什么用角度?

比较两个向量的 "相似度" 有很多方法 (欧氏距离、曼哈顿距离). RAG 通常用 余弦相似度 — 两个向量间的夹角余弦:

cos(θ) = (A·B) / (|A| × |B|)

θ = 0°   → cos = 1.0  (方向相同, 语义最相似)
θ = 90°  → cos = 0.0  (正交, 语义无关)
θ = 180° → cos = -1.0 (方向相反, 语义相反)

为什么不用欧氏距离? 因为文本长度不同会导致向量模长不同, 但语义可能一样. 余弦相似度只看 方向 (语义), 不看 模长 (长度), 更适合文本检索.

切块策略: 为什么不能整篇入库?

一篇 5000 字的文档, 如果整篇做一个 embedding, 检索时只能返回 "这篇文章相关", 不能定位到具体段落. 所以要 切块 (chunking):

shopee_tw.md (3000 字)
  ├── chunk 1: "蝦皮台灣商品標題規範: 最多120字..."     (500 字)
  ├── chunk 2: "蝦皮台灣禁止使用極限詞: 最便宜、最低價..." (500 字)
  └── chunk 3: "蝦皮台灣圖片要求: 至少5張, 白底..."      (500 字)

每块独立做 embedding, 检索时只返回最相关的 1-2 块 (top-k), 精准且省 token.

切块大小是经验值: 太大 (整篇) → 检索不准; 太小 (单句) → 上下文不足. 通常 300-800 字一块, 带一定重叠 (overlap) 避免切断语义.

kb_search 作为工具: Agent 自主检索

RAG 不是 "每次对话都检索", 而是作为 kb_search 工具注册给 Agent. Agent 判断 "这个问题我需要查知识库" 时才调用:

用户: "帮我写标题"
  → Agent: 不需要查知识库, 直接写

用户: "蝦皮标题最多几个字?"
  → Agent: 调用 kb_search(query="蝦皮標題字數限制", k=3)
  → 返回: chunk 1 "蝦皮台灣商品標題規範: 最多120字..."
  → Agent: 回复 "蝦皮标题最多 120 字"

这就是 RAG + Agent 的威力: 检索时机由模型决定, 不是硬编码的 "每次都查". 模型可能判断 "我训练数据里知道这个" 就不查, 或者 "这个我不确定" 就查.

10. M6 · Planner-Executor (DAG 规划)

M6 把 "走一步看一步" (ReAct) 升级为 "先整体规划, 再分步执行". 一次 LLM 调用把目标拆成 DAG (有向无环图), 然后按依赖拓扑排序并行执行.

为什么 ReAct "走一步看一步" 不够?

ReAct 每一步都只看 "当前状态", 没有全局视野. 这带来两个问题:

  • 无法并行: 调研和查商品没有依赖关系, 可以同时做. 但 ReAct 只能串行: 调研 → 等完 → 查商品 → 等完 → 写文案
  • 上下文膨胀: 每一步都把之前所有 Thought/Observation 带上, 到第 5 步时上下文已经很臃肿

Planner 的思路: 先用一次 LLM 调用 整体规划 (生成 DAG), 再按依赖关系 分步执行 (同层并行, 上下文裁剪).

DAG (有向无环图) 原理

Plan 本质是一个 DAG — 节点是任务, 边是依赖 ("A 依赖 B" = B 完成后才能做 A):

         t1:kb_search    t2:product_lookup      ← 第 0 层 (无依赖, 可并行)
              \              /
               \            /
                v          v
               t3: agent:writer                ← 第 1 层 (依赖 t1+t2)
                     |
                     v
               t4: platform_lint                ← 第 2 层 (依赖 t3)
                     |
                     v
               t5: agent:composer               ← 第 3 层 (依赖 t3+t4)

  "有向": 依赖关系有方向 (B → A)
  "无环": 不存在 A→B→A 的循环 (否则永远执行不完)

环检测用 Kahn 算法: 不断移除入度为 0 的节点. 如果最后还有节点没移除, 说明有环.

拓扑分层: 同层并行执行

把 DAG 按 拓扑层级 分组, 同一层的任务 没有互相依赖, 可以并行执行:

Level 0: [t1, t2]     → 并行执行 (goroutine 池, 并发度 4)
  ↓ 等待全部完成
Level 1: [t3]         → 执行
  ↓
Level 2: [t4]         → 执行
  ↓
Level 3: [t5]         → 执行 (最终输出)

并行的好处: 如果 t1 和 t2 各需 3 秒, 串行要 6 秒, 并行只要 3 秒. 任务越多, 加速越明显.

上下文裁剪: 为什么子任务只看依赖输出?

如果每个子任务都看全局历史, 上下文会指数膨胀. M6 的做法: 每个子任务的 prompt 里 只注入它依赖的任务输出:

t3 (agent:writer) 的 prompt:
  "你是一个文案写手.
   调研结果: {t1.output}     ← 只有 t1 的输出
   商品信息: {t2.output}     ← 只有 t2 的输出
   请根据以上信息写文案."

  // 不包含: system 历史、其他任务的 Thought/Observation
  // 每个 task 的上下文独立, 不互相污染

这牺牲了 "全局视野" (子任务不知道其他不依赖的任务做了什么), 但换来上下文可控 + 并行安全.

11. M7 · Multi-Agent (4 角色协作)

M7 把 "一个 Agent 干所有事" 拆成 4 个有明确边界的角色, 用消息总线协调多轮协作. 这比 M6 的 DAG 更进一步 — 不是 "任务分解", 而是 "角色分工".

为什么要拆角色?

单个 Agent 做所有事, system prompt 会很长 (又要调研、又要写、又要审), 模型注意力分散, 每个环节都做不好. 拆成 4 个角色后:

  • 每个角色的 system prompt 很短、很聚焦 — Researcher 只管调研, 不操心合规
  • 每个角色有不同的 工具子集 — Researcher 能查商品, Writer 没有工具 (纯生成)
  • 角色间有 输出契约 — Researcher 必须输出 {facts, summary}, Writer 必须输出 {title, body, tags}

这模拟了人类团队: 调研员不会替文案写手写文案, 写手不会替合规专员检查违禁词. 各司其职, 通过 "消息" 传递结果.

4 个角色的分工设计

角色职责工具输出契约审批权
Researcher调研卖点与竞品product_lookup, kb_search{facts, competitors, summary}无
Writer写文案无 (纯生成){title, body, tags}无
Critic评审吸引力slang_check{approve, issues}有
Compliance检查合规platform_lint{approve, violations}有

关键设计: 只有 Critic 和 Compliance 有 "approve" 权. Writer 不能自己说 "我写得很好" 就结束 — 必须通过评审.

消息总线: Agent 间怎么通信?

4 个角色不是直接调彼此, 而是通过 MessageBus 发消息:

// 每轮的消息流
Coordinator → Researcher:  "收集 towel 的卖点"
Researcher  → Coordinator: '{"facts":["吸水","蓬鬆"],"summary":"今治毛巾"}'
Coordinator → Writer:      "根据调研写文案. 调研: 今治毛巾..."
Writer      → Coordinator: '{"title":"今治毛巾","body":"蓬鬆吸水","tags":["#毛巾"]}'
Coordinator → Critic:      "评审: {title, body, tags}"
Critic      → Coordinator: '{"approve":false,"issues":["标题太短"]}'
Coordinator → Compliance:  "检查合规: {title, body, tags}"
Compliance  → Coordinator: '{"approve":true,"violations":[]}'

消息总线持久化到 SQLite, 所以一次完整的协作可以 回放 — 这对 M9 的 trace 和 debug 至关重要.

循环防御: bigram Jaccard 相似度

多轮协作有一个陷阱: Critic 说 "标题太短", Writer 改了但改得不够, 下一轮 Critic 还是说 "标题太短", Writer 再改... 无限循环. 我们用 文本相似度 检测这种情况:

// bigram Jaccard 相似度
// bigram = 连续 2 个字符的 pair

draft_1 = "今治毛巾 現貨免運"  → bigrams: {今治,治毛,毛巾,巾 , 現,現貨,貨免,免運}
draft_2 = "今治毛巾 現貨免運好" → bigrams: {今治,治毛,毛巾,巾 , 現,現貨,貨免,免運,運好}

similarity = |交集| / |并集| = 8 / 9 = 0.89

// 如果连续 2 轮相似度 > 0.9 → 判定 "无改进", 强制终止

为什么用 bigram 而不是字数? 因为 Writer 可能换个说法但内容一样 ("标题太短" → "标题不够长"), bigram 能捕捉这种 "换了字但没换内容" 的情况.

12. M8 · Human-in-the-Loop (人工审批)

M8 在 Agent 执行高风险动作 (发布商品 / 改库存 / 改价) 前暂停, 把决策权交给人类. 这不是 "不信任 Agent", 而是 不可逆操作必须有人兜底.

为什么需要 HITL?

Agent 可能犯三种错:

  • 幻觉: 商品不存在但 Agent "查到了", 价格是 0 但 Agent 当真了
  • 误解: 用户说 "降 20%", Agent 理解成 "降到 20%" — 价格差 5 倍
  • 合规: Agent 不知道某个词在新规则里被禁了

对于 可逆操作 (查商品、写文案), 错了可以重来. 但对于 不可逆操作 (发布、删除), 错了就是事故. HITL 在不可逆操作前插入一个 "人工确认" 节点.

风险分级: 为什么是三级?

级别含义典型操作审批策略
low可逆, 零风险查询商品、生成文案无需审批, 直接执行
medium半可逆, 有影响修改价格、更新库存可选审批 (配置开关)
high不可逆, 高风险发布商品、删除商品强制审批, 不批不执行

为什么不是二级 (要/不要)? 因为有些操作 "改了能改回来但会影响订单" (改价), 需要一个中间地带让运营灵活配置.

审批状态机

         create
            ↓
        ┌─────────┐
        │ pending │ ← 等待人类决策
        └────┬────┘
             │
    ┌────────┼────────┐
    ↓        ↓        ↓
approve   reject    edit
    │        │        │
    ↓        ↓        ↓
approved  rejected  edited
    │        │        │
    └────────┴────────┘
              │
     Agent 根据决策继续:
     approved → 用原参数执行
     rejected → 不执行, 原因返回给上一步
     edited   → 用修改后的参数执行

注意: edited 是 M8 的精髓 — 人类不只说 "行/不行", 还能说 "参数改一下再执行". 这比简单的 approve/reject 灵活得多.

13. M9 · 可观测性 + 评测

M9 解决两个问题: "Agent 到底做了什么?" (可观测性) 和 "改了 prompt, 到底变好还是变坏了?" (评测). 没有 M9, 改 prompt 就是盲改.

可观测性: Trace / Span 模型

借签 OpenTelemetry 的概念: 一次 Agent Run = 一个 Trace, 内部的每次 LLM/工具调用 = 一个 Span:

Trace (tr_abc) — "为毛巾写文案"
├─ Span (sp_1) [llm]     planner.Chat           1.2s  120→80 tokens
├─ Span (sp_2) [tool]    product_lookup         0.1s  →{"price":299}
├─ Span (sp_3) [llm]     executor.Chat          2.3s  200→150 tokens
│   └─ Span (sp_4) [llm] writer.Chat           1.8s  180→120 tokens
├─ Span (sp_5) [tool]    platform_lint          0.2s  →{"ok":true}
└─ Span (sp_6) [step]    compose_output         0.0s  →"今治毛巾..."

每个 Span 记录: kind (llm/tool/step) / input / output / tokens / error / 耗时. 通过 context.Context 透传 trace_id 和 parent span_id, 形成 调用树.

为什么用 context 透传而不是全局变量?

如果用全局变量存 trace_id, 并发时 (M6 的并行执行) 会串 — Trace A 的 span 被记到 Trace B. context 是 请求级别的, 每个 goroutine 有独立的 context 链:

// 通过 context 透传
ctx = WithTraceID(ctx, "tr_abc")       // 注入 trace_id
ctx = WithSpanID(ctx, "sp_1")          // 注入 parent span_id

// 子 goroutine 继承父 context
go func(ctx) {
    span := StartSpan(ctx, "llm")      // 自动从 ctx 取 trace_id + parent
    // → span.TraceID = "tr_abc" (正确)
    // → span.ParentID = "sp_1"   (正确)
}(ctx)

三层评测: 为什么不只用 LLM-as-Judge?

单一评测维度有盲区. M9 用三层互补:

层方法测什么局限
LLM-as-Judge用另一个 LLM 按 rubric 打 1-5 分整体质量 (吸引力/完整性)自评偏松, 不同 judge 模型分数不可比
业务度量规则计算 (黑话命中率/合规率)台湾电商特定指标只测已知模式, 不能发现新问题
成本度量token 数 + 时延效率 (改 prompt 后变快还是变慢)不测质量, 只测资源消耗

三层结合: Judge 说 4 分 (还行), 但业务度量发现黑话命中率只有 20% (不够接地气), token 上涨 50% (变贵了) → 综合判断 "改了 prompt 变差了".

LLM-as-Judge 的原理与局限

用 LLM 评 LLM 的输出, 就像让一个老师批改另一个老师的学生作业. 关键是 rubric (评分细则) 要明确:

rubric:
  1分: 与需求无关, 或包含违禁词
  3分: 基本可用, 卖点不够突出
  5分: 卖点突出, 格式完美, 有 CTA

Judge prompt:
  "按 rubric 给文案打 1-5 分.
   用户需求: {prompt}
   文案: {output}
   输出 JSON: {"score": 1-5, "reason": "..."}"

局限: 同模型自评偏松 (7B 评 7B 偏高). 更好的做法是用更大模型做 judge (14B 评 7B), 但成本更高. M10 的模型路由可以让 judge 走 14B, 被测走 7B.

14. M10 · 模型路由

M10 让 Agent 根据任务标签和上下文长度自动选择模型, 简单问题用小模型 (省时延), 复杂任务用大模型 (保质量), 失败时降级.

为什么要路由? 不全用大模型?

本地部署时, 大模型 (14B) 推理慢 (25 tok/s), 小模型 (3B) 快 (80 tok/s). 如果写一个标题也要用 14B, 用户要等 5 秒; 用 3B 只要 1.5 秒, 质量差异不大.

任务复杂度最佳模型原因
写标题低 (20 字)3B (fast)够用, 快 3 倍
写正文中 (200 字)7B (default)需要连贯性
规划 DAG高 (推理)14B (reason)需要复杂推理能力
合规检查低 (模式匹配)3B (fast)查违禁词, 不需要推理

路由的本质: 把 token 花在刀刃上. 简单任务用小模型省时延, 复杂任务用大模型保质量.

路由策略: 标签 + 上下文 + 降级

路由器用三层策略决定打哪个模型:

// 1. 任务标签路由 (最常用)
task=title      → tag:fast   → 3B模型  (fallback: 7B)
task=plan       → tag:reason → 14B模型 (fallback: 7B)
task=body       → tag:default → 7B模型

// 2. 上下文超限路由
ctx_tokens>6000 → tag:default → 7B模型  (大上下文用大模型)

// 3. 失败降级
3B 挂了 → fallback 到 7B → 7B 也挂了 → 报错
                ↑ 记录在 RouteRecord.fallbacks 里

调用方只传 task 标签 (如 "title" / "plan" / "body"), 路由内部决定打到哪. 这意味着 agent 代码完全不需要知道有几个模型 — 路由器是透明的.

降级机制: 为什么不直接报错?

本地部署时, 某个模型可能因为显存不足、并发冲突等原因暂时不可用. 如果直接报错, 用户体验是 "Agent 挂了". 降级机制让 3B 挂了自动切 7B, 用户无感知:

// 降级流程
primary = 3B  → client.Chat()  → error (模型不可用)
                                      ↓
fallback[0] = 7B → client.Chat()  → success! ✓
                                      ↓
RouteRecord:
  chosen = "7B"           // 最终命中的
  fallbacks = ["3B"]      // 尝试过但失败的
  success = true

代价: 降级后可能比预期慢 (7B 比 3B 慢). 但 "慢" 总比 "挂" 好.

15. M11 · Capstone (毕业项目)

M11 把 M0-M10 的能力组合成完整电商文案 Agent: 一条命令完成多平台文案生成 + 评测. 这是整个项目的 集成验收 — 如果 M0-M10 有 bug, Capstone 跑不通.

流水线编排: M0-M10 能力串联

输入: seller=A001, sku=sku_001, platforms=[shopee, xhs], style=girlfriend
  │
  ├─ 对每个 platform:
  │   │
  │   ├─ M7: Multi-Agent 协作 (4 角色, 多轮)
  │   │   ├─ Researcher → 调研卖点 (用 M2 工具 + M5 RAG)
  │   │   ├─ Writer → 写文案 (用 M4 记忆偏好)
  │   │   ├─ Critic → 评审 (循环防御防死循环)
  │   │   └─ Compliance → 合规检查
  │   │
  │   └─ M9: 评测
  │       ├─ LLM-as-Judge → 打 1-5 分
  │       ├─ 业务度量 → 黑话命中率 + 合规率
  │       └─ 成本度量 → token + 时延
  │
  ├─ M10: 模型路由 (隐式)
  │   ├─ title 任务 → 3B
  │   ├─ body 任务 → 7B
  │   └─ plan 任务 → 14B
  │
  └─ 输出: 多平台文案 + 评测分数 + markdown 报告

评测对比: 为什么要有 baseline?

M11 的真正价值不是 "能跑通", 而是 "改了之后能不能量化对比":

# 第一次: baseline
go run ./agent-lab/cmd/eval -tag baseline
→ judge=3.2  slang=45%  compliance=80%  tokens=2800

# 改了 system prompt (加入黑话引导)

# 第二次: improved
go run ./agent-lab/cmd/eval -tag improved
→ judge=4.1  slang=78%  compliance=100%  tokens=3100

# 结论: 改进有效!
  judge +0.9 (质量提升)
  slang +33% (更接地气)
  compliance +20% (合规提升)
  tokens +11% (成本略增, 可接受)

没有 M9 的评测, "改 prompt" 就是凭感觉. 有了评测, 每次改进都有数据支撑 — 这是工程化 Agent 的基础.

风格系统: 4 种文案人格

同一个商品, 不同平台 / 不同目标用户需要不同风格. M11 内置 4 种风格:

风格语气适用场景示例
girlfriend亲切闺蜜, 多 emoji小红书种草"姐妹们! 这个毛巾真的太好用了~ 🥰"
promo促销紧迫, 强调限时蝦皮限时特卖"限時下殺! 現貨免運 最後3小時!"
pro专业规格, 突出认证momo 3C 类目"316不鏽鋼 SGS認證 保固一年"
gift送礼场景, 强调包装节日送礼"精美禮盒包裝 送禮首選 體面大方"

风格通过 StylePersona() 返回一段补充 prompt, 注入到 Multi-Agent 的 goal 中: "风格: 亲切闺蜜, 多 emoji". Writer 角色会据此调整语气.

工程基线: 用 Capstone 做回归测试

每次改代码 (修 bug / 加功能) 后, 跑一次 Capstone, 确保没有 regression:

# CI/CD 中的回归测试
go run ./agent-lab/cmd/capstone \
  --seller A001 --sku-id sku_001 \
  --platforms shopee,xhs --style girlfriend

# 验收标准:
# 1. status=ok (不能 fail)
# 2. compliance_rate=100% (不能有违禁词)
# 3. judge_score >= 3.0 (不能太差)
# 4. duration < 60s (不能太慢)

这就是 "从零手写 Agent" 的终点: 不只是能跑, 而是 可观测、可评测、可回归. 这三个 "可" 是 Agent 工程化的基础.

16. 本地大模型

agent-lab 不绑定任何云端 API。只要它在 OPENAI_BASE_URL 上暴露 Chat Completions 协议，就能接进来. 三种方式:

方式适用硬件启动命令对应的 BASE_URL
llama.cpp CPU / NVIDIA GPU ./llama-server -m qwen2.5-7b-instruct-q5_k_m.gguf -c 4096 --port 8080 http://127.0.0.1:8080/v1
Ollama macOS / Linux / Win ollama run qwen2.5:7b http://127.0.0.1:11434/v1
fake-openai (台湾电商文案模拟器) 任何机器 go run ./agent-lab/scripts/fake-openai http://127.0.0.1:18080/v1

fake-openai 是什么?

它不是 LLM — 是一个会解析 system prompt 与历史消息、按风格输出繁体中文电商文案的规则模拟器。好处是:

  • 零依赖, 零模型下载, 零 GPU
  • 完整兼容 OpenAI Chat Completions 协议 (stream=true / usage 字段)
  • 支持 4 种风格: 亲切 / 促销 / 专业 / 年轻 / 送礼
  • 会自动识别商品名、品牌、价位、平台等信息槽位

完整启动脚本 (Windows)

# 终端 A — fake-openai (台湾电商文案模拟器)
go run .\agent-lab\scripts\fake-openai

# 终端 B — Web UI
set OPENAI_BASE_URL=http://127.0.0.1:18080/v1
set OPENAI_API_KEY=sk-local
set AGENTLAB_PROFILE=L
go run .\agent-lab\cmd\web

# 打开浏览器访问:  http://127.0.0.1:8090/chat

# 也可以走 CLI REPL
go run .\agent-lab\cmd\chat

默认 profile (AGENTLAB_PROFILE=L) 对应模型 qwen2.5-7b-instruct, 其他档位:

  • S: qwen1.5-1.8b-chat (树莓派也能跑)
  • M: qwen2.5-3b-instruct
  • L: qwen2.5-7b-instruct (推荐)
  • XL: qwen2.5-14b-instruct
