🧠 agent-lab 设计教程

从零手写一个 Agent 的学习路径 · 纯 Go · 本地大模型

1. 这是什么 / 为什么要做

纯 Go本地模型教学导向

市面上的 Agent 框架太多 (LangChain / LlamaIndex / AutoGen...), 每一个都有一堆概念要学. 本项目反其道而行 — 自己手写一个.

目标不是替代框架, 而是:

  • 看见每一根线: 从 HTTP 调用到 SSE 流式, 一行一行自己写.
  • 用统一业务场景 (台湾电商文案) 贯穿所有里程碑, 不切换上下文.
  • 不依赖云端 API — 没有 GPU 也能用 fake server 跑通流程.

2. 分层架构

Agent 拆成 4 个水平层：入口 → 应用 → 领域 → 基础设施。上层调用下层提供的能力，不反向依赖。下面每一层的职责和对应的 Go 文件：

入口 Entry用户看得见的入口：命令行 / 浏览器
cmd/chat (REPL) cmd/web (HTTP)
▼ 调用
应用 App把请求串成业务动作
internal/web · Chat handlers internal/web · SSE 流式 internal/web · ConversationStore
▼ 调用
领域 Domain记忆 + 角色卡，核心逻辑
internal/memory (会话记忆) internal/prompt (角色卡 + 模板) internal/tools (M2+ 工具调用)

说明：分层架构的意义是让"业务会不会写文案"和"网络怎么连接模型"两个问题解耦。将来要换模型、换浏览器 UI 时，只改最底层或最上层，不需要动中间的领域层。

2.1 一条用户消息的数据流

用户在浏览器里输入一句话，点击"发送"后，这条消息会依次经过以下 5 个"处理节点"，最终以字符流的形式回到浏览器。每个节点对应一段可单独打开看的源码文件。

① 浏览器HTML + JS
chat.js 发 fetch
→
② chat API handlerinternal/web/handlers_chat.go
POST /api/chat
→
③ 会话记忆internal/memory/shortterm.go
Append + EnsureBudget
→
④ LLM 协议internal/llm/client.go
ChatStream (OpenAI 兼容)
→
⑤ 真正的模型llama.cpp / Ollama / fake-openai
POST /v1/chat/completions

回复的路径是反向的：⑤ 把 data: {"content":"..."}\n\n 的 SSE 帧流式吐给 ④ → ④ 写回给 ② 的 http.Flusher → ② 原样转发给浏览器 → 浏览器 chat.js 拼接并显示。

2.2 一次完整调用链（6 步）

1

用户输入 → HTTP POST /api/chat

浏览器发起 JSON 请求：{"conversation_id":"...","message":"写文案..."}。如果是首次发送，conversation_id 为空，服务端会新建一个。

2

handlers_chat.go · handleChatAPI()

定位到 ConversationStore，把用户消息写入该会话的 ShortTerm（即 memory 里的消息历史）。如果上下文已超出 token 预算，这里会触发滑窗 / 摘要。

3

memory.Snapshot() → 构造 messages 数组

把 [system, user, assistant, user, assistant, ...] 拼成 OpenAI 协议要求的 JSON 数组。system 来自角色卡，每轮 user/assistant 来自历史消息。

4

llm.OpenAIClient.ChatStream()

向 OPENAI_BASE_URL 发起 POST /v1/chat/completions，请求里带 stream=true，模型会以 text/event-stream 形式一块一块返回。

5

handlers_chat.go · writeSSE()

收到的每一段 content delta，立刻转成浏览器认识的 SSE 帧：event: delta\ndata: {"content":"..."}\n\n，并调用 http.Flusher.Flush() 立刻写回 TCP 连接。这一步让字一个一个出现。

6

chat.js onmessage → 拼接并渲染

浏览器端监听 event: delta，把每次 content 追加到一个字符串，再塞进气泡 div 的 innerText。流式结束时收到 event: done，聊天条标记完成。

4. M0 · 最小骨架

M0 要做的事非常简单: 发一条消息给 LLM, 流式收到回复. 关键是把 可运行的骨架 搭好.

核心数据结构

// llm/client.go — 与 OpenAI 兼容 server 通信的最小接口
type Message struct {
    Role    Role   `json:"role"`
    Content string `json:"content,omitempty"`
}
type ChatRequest struct {
    Model    string    `json:"model"`
    Messages []Message `json:"messages"`
    Stream   bool      `json:"stream,omitempty"`
}
type Client interface {
    Chat(ctx, req) (ChatResponse, error)
    ChatStream(ctx, req) (<-chan StreamChunk, error)
}

启动方式 (Fake Server + Web)

# 终端 A: 启动 fake LLM server (echo 模式, 不需要真实模型)
go run ./agent-lab/scripts/fake-openai

# 终端 B: 启动 Web UI
set OPENAI_BASE_URL=http://127.0.0.1:18080/v1
set OPENAI_API_KEY=sk-local
set AGENTLAB_PROFILE=L
go run ./agent-lab/cmd/web
# 浏览器打开 http://127.0.0.1:8090

5. M1 · 多轮对话

M1 引入两个新模块:

internal/memory/shortterm.go — 会话记忆

提供 ShortTerm 结构, 负责:

  • 存储 system + [user, assistant, user, assistant, ...] 的消息序列
  • 粗略估算 token (中文 1.5 字 ≈ 1 token, 英文 4 字 ≈ 1 token)
  • 超出预算时先滑窗丢最旧的, 再不行就调 LLM 把最旧一半摘要成一条
  • 支持 :save / :load 到 JSON 文件

internal/prompt/persona.go — 角色卡

一个 persona = 一个 system prompt. 支持从 .md 文件加载, 方便换风格.

关键调用流

1. 用户输入 → memory.Append(user, 输入)
2. memory.EnsureBudget(ctx, client, model, maxTokens)  // 检查 & 压缩
3. msgs := memory.Snapshot()  // [system, ...history]
4. client.ChatStream(ctx, {Model: model, Messages: msgs})
5. 收集流式回复 → memory.Append(assistant, 完整回复)

Web UI 的改变

  • 左侧新增"会话列表", 新建 / 切换 / 重命名 / 删除
  • 顶部角色卡编辑区, 保存后下一条消息生效 (不重写历史)
  • 服务端压缩时, UI 在消息流中插入一行灰色提示: "摘要: 压缩 N 轮 → M tokens"
  • 底部按钮: Reset / Export / Import

6. M2 · 原生 Tool Calling

M2 让模型 自己决定要不要调工具. 利用 OpenAI 协议里的 tools + tool_calls 字段, 模型在合适的时候输出工具名和参数, 我们执行后把结果喂回去.

关键文件

  • internal/tools/ — Tool 接口 + Registry: product_lookup (查商品), price_format (格式化价格), platform_lint (平台合规), slang_check (黑话检查)
  • internal/agent/native.go — Loop(): LLM → tool_calls → 执行 → 喂回 → 再 LLM, 直到模型不再调工具
  • internal/web/handlers_tools.go — /tools 面板: 试调用 (DryRun) 工具, 不经过 LLM
// Loop 的核心循环 (最多 MaxSteps 轮)
for step := 0; step < maxSteps; step++ {
    resp = client.Chat(ctx, req)           // 1. 问 LLM
    if len(resp.ToolCalls) == 0 { break }   // 2. 没有工具调用 → 结束
    for _, tc := range resp.ToolCalls {     // 3. 执行每个工具
        out = registry.Get(tc.Name).Invoke(ctx, tc.Args)
        messages = append(messages, toolResult(out))  // 4. 喂回结果
    }
}

7. M3 · 手写 ReAct

如果模型不支持 tool_calls (或你想理解原理), M3 手写 Thought-Action-Observation 文本协议. 模型输出 JSON {"thought":"...","action":"tool_name","args":{...}}, 我们解析后执行, 再把 {"observation":"结果"} 喂回去.

关键文件

  • internal/agent/react.go — Loop() ReAct 版本: system prompt 约定 JSON 格式, 解析容错 (裸 JSON / ```json / 大括号提取)
  • internal/agent/parse.go — 容错 JSON 提取: extractFenced / extractFirstBracePair
  • Chat 面板底部 agent 模式 下拉可切换 native / react

native vs react: native 靠模型原生能力 (更快更准), react 靠 prompt 工程 (兼容性更好, 但多一轮解析开销). 两者共享同一套工具.

8. M4 · 记忆 (短期摘要 + 长期 KV)

M4 给 Agent 加 "记住卖家偏好" 的能力. 两层记忆:

短期记忆 (M1 已有, M4 增强)

滑窗 + 摘要: 上下文超预算时, 先滑窗丢最旧消息, 再不够就把旧消息摘要成一条. M4 把摘要也做成了 tool (memory_summarize).

长期记忆 (M4 新增)

  • internal/memory/kv.go — KV 结构: namespace + key → value, 持久化到 SQLite
  • 两个工具: memory_put (写入) / memory_get (读取)
  • namespace = seller:ID, 让不同卖家的记忆隔离
  • Chat 面板底部 seller: 输入框决定当前 namespace
# agent 自动写入的长期记忆示例 (SQLite kv_store 表)
namespace=seller:A001, key=tone,       value="亲切活泼, 多用 emoji"
namespace=seller:A001, key=keywords,   value=["現貨","免運","下殺"]
namespace=seller:A001, key=audience,   value="小资女, 25-35岁"

/memory 面板可浏览全部长期记忆, 并 "遗忘" 单条.

9. M5 · RAG (向量检索)

M5 让 Agent 能查 "知识库" — 平台规则文档、商品资料等. 不把文档塞进 prompt, 而是用 embedding + 向量 top-k 只检索相关片段.

关键文件

  • internal/rag/ — Retriever: embedding → 余弦相似度 → top-k
  • internal/store/ — SQLite 存储 documents 表 (id / source / chunk / embedding BLOB)
  • internal/tools/kb_search.go — kb_search 工具: Agent 自主决定何时检索
  • cmd/ingest/ — 把 .md 文档切块 + embedding 入库
# 导入平台规则到知识库
go run ./agent-lab/cmd/ingest -dir agent-lab/data/platform_rules
# → shopee_tw.md (2 chunks) + xiaohongshu.md (1 chunk) = 5 个文档块

# Agent 调用 kb_search 工具
{"query": "蝦皮標題字數限制", "k": 5}
# → 返回最相关的 top-5 文档块

/knowledge 面板可手动检索测试, 查看命中片段与相似度分数.

10. M6 · Planner-Executor (DAG 规划)

M6 把 "走一步看一步" (ReAct) 升级为 "先整体规划, 再分步执行". 一次 LLM 调用把目标拆成 DAG (有向无环图), 然后按依赖拓扑排序并行执行.

关键文件

  • internal/agent/planner.go — Planner.Plan(): LLM → Plan JSON, 解析失败重试
  • internal/agent/executor.go — Executor.Execute(): DAG 拓扑分层, 同层并行 (并发度 4), 失败 Replan
  • internal/agent/plan_types.go — Plan / Task / TaskStatus / Kahn 环检测 / TopoLevels
  • cmd/plan/ — CLI: -m "目标" 生成 DAG → 执行 → dump JSON
# 典型 DAG: 调研 → 查商品 → 写文案 → 合规检查 → 组合输出
t1: kb_search (无依赖)
t2: product_lookup (无依赖)
t3: agent:writer (depends: t1, t2)   ← 并行等 t1+t2 完成后执行
t4: platform_lint (depends: t3)
t5: agent:composer (depends: t3, t4) ← 最终输出

# /plan 面板: 输入目标 → 生成计划 → 执行计划 (DAG 节点实时变色)

上下文裁剪: 每个 agent 子任务只看自己依赖的输出 ({t1.output}), 不看全局历史, 避免 token 膨胀.

11. M7 · Multi-Agent (4 角色协作)

M7 把 "一个 Agent 干所有事" 拆成 4 个有明确边界的角色, 用消息总线协调多轮协作.

4 个角色

  • Researcher (调研员): 收集商品信息与卖点 → {facts, competitors, summary}
  • Writer (撰稿人): 根据调研写文案 → {title, body, tags}
  • Critic (评审): 检查吸引力与完整性 → {approve, issues}
  • Compliance (合规): 检查平台规则 → {approve, violations}

关键文件

  • internal/agent/bus.go — MessageBus: agent 间消息传递, 持久化到 SQLite
  • internal/agent/roles.go — 4 个角色的 system prompt + 工具子集 + 输出契约
  • internal/agent/multi.go — MultiAgent.Run(): 多轮协作 + 终止条件 + 循环防御
  • cmd/multi/ — CLI: -m "目标" 启动 4 角色协作
每轮流程:
  Researcher → Writer → Critic + Compliance
                                ↓
                   都 approve → 完成 ✓
                   不通过 → 合并 issues+violations → 反馈给下一轮 Writer ↻

终止条件:
  1. Critic + Compliance 都 approve → status=ok
  2. 达到 maxRounds (默认 4) → status=max_rounds
  3. 循环防御: 连续 2 轮 draft 相似度 > 90% → status=stale (无改进)

/multi 面板: 4 列消息流 (每列一个角色) + 轮次状态 + 反馈区. 每轮每角色的输出实时显示在对应列.

12. M8 · Human-in-the-Loop (人工审批)

M8 在 Agent 执行高风险动作 (发布商品 / 改库存 / 改价) 前暂停, 把决策权交给人类.

风险分级 (RiskLevel)

  • low (绿): 可逆操作 (查询/生成文案), 无需审批
  • medium (橙): 半可逆操作 (改价), 可选审批
  • high (红): 不可逆操作 (发布), 强制审批

工具可选实现 RiskLeveler 接口, 未实现时默认 low.

关键文件

  • internal/hitl/approval.go — Approval + Manager: Create / Approve / Reject / Edit, 持久化到 SQLite
  • internal/tools/tool.go — RiskLevel / RiskLeveler / GetRiskLevel()
  • cmd/hitl/ — CLI: list / show / approve / reject / edit
三种审批决策:
  approve  → 直接放行, Agent 继续执行
  reject   → 拒绝, 原因返回给上一步角色
  edit     → 修改参数后放行, Agent 用 edited_args 继续执行

/approvals 面板: 待审批表格 (风险徽标颜色) → 点击查看详情 → 批准 / 拒绝 / 修改参数.

13. M9 · 可观测性 + 评测

M9 给 Agent 加统一 trace (所有 LLM / 工具 / step 调用可结构化查询), 建立三层评测让 "改了 prompt 比之前更好" 有数据支撑.

Trace / Span

  • internal/trace/trace.go — Trace (一次 Run) + Span (一次调用), 通过 context.Context 透传
  • Span kind: llm / tool / step / agent, 含 input/output / tokens / error / 耗时
  • 持久化到 SQLite (traces + spans 表)
  • cmd/trace/ — CLI: list / show / export

三层评测

  • LLM-as-Judge (internal/eval/judge.go): 用 rubric 让 LLM 给输出打 1-5 分
  • 业务度量 (internal/eval/metrics.go): 黑话命中率 (現貨/免運/CP值...) + 平台合规率 (违禁词检查)
  • Runner (internal/eval/runner.go): 跑固定 prompts → agent 输出 → judge + metrics → markdown 报告
# 跑评测
go run ./agent-lab/cmd/eval -suite ecom-v1 -tag baseline
# → 6 条用例, 输出 markdown 报告 (Judge 均分 / 黑话命中率 / 合规率 / token / 时延)

# 查 trace
go run ./agent-lab/cmd/trace list
go run ./agent-lab/cmd/trace show

/traces 面板: 左侧 trace 列表 (状态颜色) → 右侧 span 时间线 (llm 蓝 / tool 绿 / step 紫 / agent 橙), input/output 可折叠.

14. 本地大模型

agent-lab 不绑定任何云端 API。只要它在 OPENAI_BASE_URL 上暴露 Chat Completions 协议，就能接进来. 三种方式:

方式适用硬件启动命令对应的 BASE_URL
llama.cpp CPU / NVIDIA GPU ./llama-server -m qwen2.5-7b-instruct-q5_k_m.gguf -c 4096 --port 8080 http://127.0.0.1:8080/v1
Ollama macOS / Linux / Win ollama run qwen2.5:7b http://127.0.0.1:11434/v1
fake-openai (台湾电商文案模拟器) 任何机器 go run ./agent-lab/scripts/fake-openai http://127.0.0.1:18080/v1

fake-openai 是什么?

它不是 LLM — 是一个会解析 system prompt 与历史消息、按风格输出繁体中文电商文案的规则模拟器。好处是:

  • 零依赖, 零模型下载, 零 GPU
  • 完整兼容 OpenAI Chat Completions 协议 (stream=true / usage 字段)
  • 支持 4 种风格: 亲切 / 促销 / 专业 / 年轻 / 送礼
  • 会自动识别商品名、品牌、价位、平台等信息槽位

完整启动脚本 (Windows)

# 终端 A — fake-openai (台湾电商文案模拟器)
go run .\agent-lab\scripts\fake-openai

# 终端 B — Web UI

set AGENTLAB_PROFILE=L
go run .\agent-lab\cmd\web

# 打开浏览器访问:  http://127.0.0.1:8090/chat

# 也可以走 CLI REPL
go run .\agent-lab\cmd\chat

  • S: qwen1.5-1.8b-chat (树莓派也能跑)

15. 接下来要学什么

用 M9 的评测打底, 把简单问题路由给小模型 (省 token), 复杂任务路由给大模型 (保质量). "路由收益" 可量化: 对比路由前后的 Judge 均分与 token 成本.

M11 · 毕业项目

用 M6 Planner + M7 Multi-Agent + M8 HITL + M9 Eval 组装一条完整的电商文案生成流水线: 接需求 → 规划 → 多角色协作 → 人工审批 → 评测出报告.
