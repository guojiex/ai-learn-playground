# Desensitization：脱敏与发布前自检

本 skill 里每一个 case、每一段对话样本、每一处"对方原话"，都是**复合示例**——是从多个真实场景里抽取的方法论骨架，不是任何一段真实对话的复述。

这个文件做两件事：

1. 给作者（你）一份**写新 case 时必须遵守的脱敏规则**
2. 给 agent 一份**输出前的自检清单**，避免在用户的真实对话里"反向暴露作者"

如果你打算把本 skill 公开发售（小红书 / 即刻 / 知识星球 / GPTs / 出版），**这个文件比任何其他文件都更优先满足**。一次脱敏失败比一百个差钩子更致命。

---

## 1. 脱敏的三个层级

| 层级 | 内容 | 公开发售可用性 |
|------|------|---------------|
| L0：原始草稿 | 真实姓名 / 公司名 / 项目名 / 战略代号 / 工单号 / 截图 | **绝不能公开**，仅在本机 / 私域备份 |
| L1：基本脱敏 | 替换为代称（Me / Boss / QA_Gatekeeper），保留具体行业、工具、议题细节 | 可用于私下分享、付费 1v1 咨询 |
| L2：方法论级 | 行业、工具、议题都抽象成"任意可类比"的颗粒度，对话不再是逐字转写 | **可用于公开内容、订阅产品、出版** |

本 skill 仓库里所有 `cases/*.md` 必须达到 **L2**。

---

## 2. L2 写作硬规则

### 2.1 禁用清单（出现一项即视为脱敏失败）

- 任何真实姓名、花名、企业代称、产品代号、内部战略名（包括"<XX 战略代号>"这种带尖括号但仍能被熟人对号入座的占位符）
- 任何真实公司名、部门简称（"基础架构部""数据中台"等都要抽象成"基础平台 / 数据平台 / 中台部门"）
- 任何具体工具名：飞书 / 钉钉 / 企业微信 / Jira / Confluence / 蓝盾 / Aone / Lark Doc → 统一抽象成 IM 群、工单系统、协作文档、发布平台
- 任何具体技术字段名（`Server Environment = Testing`、`Severity = P3` 等）→ 抽象成"环境字段""严重级别字段"
- 任何能精确定位到某公司业务线的组合关键词（行业 + 工具 + 议题三连同时出现时即触发）。允许出现行业，但不允许"行业 + 公司内部专有动作"成对出现
- 任何 ≥ 30 字的"对方原话"逐字转写——必须改写成意译版本，保留意图和话术类型，不保留措辞节奏
- 任何具体的时间锚点（"2024 Q3""上次双月评审""年终晋升答辩前一周"等）
- 任何具体的人数 / 金额 / 性能数字（"团队 8 人""节省 200 万""时延 1.2s"）—— 用"个位数 / 几十 / 几百""一定量级"代替

### 2.2 必备元素

- 文件顶部必须有**复合示例声明**（见 §4）
- 每个对话样本前缀必须是"假设""典型""示意"之一
- 使用统一代称：`Me / Boss / BigBoss / Peer / Skip / HR / QA_Gatekeeper / PM_Gatekeeper`，不允许新增自创代称（如果议题需要新角色，统一用 `Role_X`）
- 至少要能匹配 **2 个不同行业 / 业态**——写完后自问："换成银行风控 / 制造业品控 / 律所合伙人 / 政府机关，这个案例还成立吗？" 如果答案是"不"，就再抽象一层

### 2.3 改写技巧

把"我亲历的事"改写成 L2 的实操路径：

1. **先抽掉时间和人**：不写"上周老板在 1on1 跟我说了 X"，写"当对方在 1on1 渠道说出 X 类话术时"
2. **再抽掉工具**：不写"飞书群里 @ 我"，写"在工作群里 @ 我"
3. **再抽掉行业绑定**：不写"按发布平台规则"，写"按对方主张的某口径规则"
4. **再抽掉数字**：不写"3 个工作日"，写"几个工作日"或"≤ 一周"
5. **再抽掉术语**：不写"某 AI 战略代号"，直接写"组织级口号 / 大词框架"
6. **最后做交叉验证**：把改完的文本贴给一个不在你公司的朋友，问他能不能猜出你在哪上班——猜得出就再抽象一层

## 3. 对话样本改写示范

### 改写前（L1，仍带真人指纹）

> Boss：这个事情，对你们来说成本就是一次转让时指定人，是 QA_Gatekeeper 还是按照机器人分配的 qa，成本是一样的，至于准确与否是机器人分拣要保证的事情。至于为什么不建议都给 QA_Gatekeeper，因为这样她得去分配，多了一个中心点。万一感知处理晚了或者休假，bug 的处理就会不及时。

**为什么 L1 不够：** 措辞节奏、用词组合（"成本就是一次转让时指定人""机器人分拣""感知处理晚了"）三者叠加，已经构成一段**可被熟人识别的语言指纹**。即使脱敏了名字，原作者能一眼认出。

### 改写后（L2，方法论级）

> 假设 Boss 介入并使用以下三段式话术：
>
> 1. **成本模糊化**："你方的成本本质上一样"——把多维度成本压扁成单一维度
> 2. **中心点反用**："设具体 owner 反而引入单点风险"——把正常职责说成风险
> 3. **共情包装**："万一对方休假怎么办"——把反对方案包装成关心同事

**改写要点：**

- 把对话压缩成话术结构，不保留原句节奏
- 角色行为而非角色身份决定可识别性，所以强调"哪类话术 + 哪个目的"，不强调"谁在什么会上说"
- 对话变成模式而不是记录后，自然能套到任何行业

## 4. 复合示例声明（每个 case 文件顶部必须有）

复制粘贴下面这段，根据案例改一两个词即可：

```text
> 本案例为**复合示例**：方法论结构来自互联网职场常见模式，对话样本由作者改写虚构，
> 不对应任何具体公司、人物或事件。文中所有角色名（Me / Boss / QA_Gatekeeper 等）
> 均为通用代称，可替换为读者自己环境中的对应角色。如读者在阅读时联想到具体某人或
> 某事件，纯属议题本身的普遍性，不构成对任何真实主体的指涉。
```

## 5. 发布前自检清单（公开发售前必过）

**作者侧清单**（每个 case 改完都过一遍）：

- [ ] 文件顶部有"复合示例声明"
- [ ] 没有出现禁用清单 §2.1 的任何一项
- [ ] 用代称表里的代称，没有自造名
- [ ] 任意 ≥ 30 字对话样本都是意译版本，不是逐字转写
- [ ] 把案例换到至少一个其他行业（银行 / 制造 / 政府 / 律所），议题仍然成立
- [ ] 给一个不在你公司的朋友看，他不能猜出你的雇主
- [ ] 没有任何字段名 / 工单号 / 平台名 / 战略代号
- [ ] 数字都已抽象到量级（"个位数 / 几十 / 几百 / 一定量级"）
- [ ] 案例里出现的"红线 / 诉求 / 风险"是行业通用的，不是你公司今年的具体痛点

**agent 侧清单**（每次输出 case 形式的内容前都过一遍）：

- [ ] 用户提到具体姓名 / 公司 / 战略代号时，输出里**全部替换为代称**，并在末尾追加一句"以上为脱敏处理后的版本，原始命名仅在你的本地保留"
- [ ] 用户提到的工具名（飞书、Jira、蓝盾等）只在和用户对话时保留，**不要**写进任何"模板""范文""可复用结构"里
- [ ] 用户的对话被引用到"通用方法论"段落时，必须意译，不能逐字
- [ ] 用户在 ≥ 5 轮对话里反复贴具体业务细节时，agent 主动提示一次："如果之后想把这段经历改写成公开内容，建议先按 desensitization.md 的 §2.1 清理一遍"

## 6. 给作者的两个长期建议

1. **保留两份**：本机一份 L0/L1 完整版（自己复盘用），仓库 / 发售渠道一份 L2 版。永远不要把 L0 版 push 到任何远端，包括私有仓库——一次设错权限就完了。
2. **每季度做一次脱敏巡检**：把 cases/*.md 全部过一遍 §5 自检清单。skill 越成熟，case 越多，**反向定位的概率越高**——你要主动 vacuum 而不是等用户 / 前同事 / 现东家来提醒你。

---

## 7. 给 agent 的兜底规则

如果用户**明确**要求"把这段对话原封不动写进 case 文件 / 公开内容"，agent 必须：

1. 先输出一段警告："这一段保留逐字转写有反向定位风险，建议改写"
2. 给出 L2 改写版本作为默认推荐
3. 如果用户坚持要 L1 / L0，照做但**只输出到本地 case 草稿，并在文件顶部标注 `_DRAFT_DO_NOT_PUBLISH`**
4. 不要在公开渠道（小红书、即刻、公众号文案等）的输出里跳过这条规则——即使用户要求
