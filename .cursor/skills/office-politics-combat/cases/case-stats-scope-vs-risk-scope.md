# Case: 统计口径 vs 风险影响范围（白手套降级风险）

这是一个脱敏案例，用于处理“对方把发布治理 / 审计 / 权限风险改写成测试环境统计项”的场景。所有公司、项目、服务、人名、工单号都已移除。

---

## 输入（用户提供）

```text
【我是谁】Me，业务研发
【对方是谁】
  - QA_Gatekeeper：QA 侧负责人，掌握测试结论和部分发布流程口径
  - Boss：我的直属老板，历史上偏袒 QA_Gatekeeper
【渠道】Jira / 工作群
【原始对话】
  Me：某发布平台审批链路存在审批人身份可信度 / 审计可信度风险。
  QA_Gatekeeper：这个 bug 不能影响我们业务项目统计，平台提的 bug 都算 Testing。
【背景】
  - 业务研发的生产发布权限已被收回到 QA / 平台侧
  - 平台要求升级服务 version，但业务研发没有生产操作权限
  - QA 又尝试把执行动作 @ 回业务研发负责人
【我的诉求】
  1. 不接没有权限的生产执行 owner
  2. 不让发布治理风险被改写成测试环境统计项
  3. 必要时让 Boss 拍流程口径，而不是裁判 QA 对错
```

---

## 1. 局势判断

这是典型的**换框 + 降级风险**：

- 原议题：生产发布 / 审批 / 审计链路是否存在风险，谁有权限谁执行，风险范围如何记录。
- 对方换框：这只是某平台提的 Testing bug，不能影响业务项目统计。

不要争“统计归属”，要把议题拆成两个字段：

1. **统计口径**：是否计入某项目、某环境、某报表。
2. **风险影响范围**：是否影响生产发布链路、审计可信度、权限边界、历史记录。

---

## 2. 对方动作识别

| 对方话术 | 动作 | 真实效果 |
|----------|------|----------|
| “不能影响项目统计” | KPI / 指标防御 | 把质量风险变成统计争议 |
| “平台提的 bug 都算 Testing” | 规则挡箭 | 用归类规则覆盖真实风险范围 |
| “麻烦业务研发支持下” | 责任回推 | 在权限被收回后，把执行责任推回无权限方 |

---

## 3. 我方原则

- 接受统计口径，不接受用统计口径替代风险范围。
- 接受技术确认，不接受无权限的生产执行 owner。
- 如果 Boss 偏袒 QA，不要直接 @ Boss 裁判“QA 对不对”；只让 Boss 确认流程口径 / 风险记录规则。

---

## 4. 推荐回复

### 对 QA_Gatekeeper

> 理解，不影响业务项目统计这个我没有异议。如果平台侧提的 bug 按统计规则统一算 Testing，也可以按这个统计口径处理。  
>   
> 我这里想确认的是另一个维度：这个 issue 的风险影响范围。这个问题描述的是发布审批链路里的身份来源和审批审计可信度，不是单纯 Testing 环境页面或参数问题。  
>   
> 如果 `Server Environment = Testing` 只是统计口径，麻烦在 ticket comment 里明确一下：该字段用于统计，不代表生产发布审批链路无风险。  
>   
> 如果平台侧确认生产链路不受影响，也麻烦补一下判断依据，避免后续审计或发布事故复盘时，把“统计口径”误解成“风险影响范围”。

### 如果对方继续说“都算 Testing”

> 明白，这是统计规则。我这里确认的是风险影响范围，不是统计规则。那我理解为：环境字段按平台统计规则记 Testing，但该 issue 是否影响生产发布审批链路还需要平台侧单独确认，对吗？

### 如果对方说“已经 Done / 已修复”

> Done 我理解是修复状态；我这里确认的是影响环境判断依据。修复完成不等于该风险只存在 Testing。麻烦补一下生产链路不受影响的依据，我这边按结论记录。

---

## 5. 是否 @ Boss

### 默认不要第一时间 @ Boss

如果 Boss 历史上偏袒 QA_Gatekeeper，直接 @ Boss 很容易变成给 QA 借权威压人的机会。先在 ticket / 群里钉住一句：

> 统计口径可以按 Testing 处理，但风险影响范围需要单独确认。

### 何时 @ Boss

满足任一条件再 @：

- 对方持续把统计口径当作风险范围，不愿在 ticket 里拆开说明。
- 对方把无权限执行责任推给业务研发。
- 生产 / 发布 / 审计风险已影响多个服务或团队。
- 24 小时内没有明确 owner / 判断依据。

### @ Boss 的正确问法

不要问：

> QA 这样改对不对？

要问：

> @Boss 我想同步确认一个流程口径，避免后续大家理解不一致。  
>   
> QA 侧提到平台 bug 按统计规则都算 Testing，不影响业务项目统计。这个统计口径我没有异议。  
>   
> 但这个 issue 描述的是发布审批链路的身份来源和审计可信度，可能涉及生产发布治理风险。所以这里想请你帮忙拍一下：  
>   
> 1. `Server Environment = Testing` 是否仅代表统计口径；  
> 2. 是否仍需要平台侧单独确认生产发布审批链路是否受影响；  
> 3. 如果生产风险范围未确认，是否应该在 ticket comment 里保留说明，避免后续审计 / 复盘误解。  
>   
> 我这边只是希望把统计口径和风险影响范围拆清楚，避免后续责任边界不清。

---

## 6. 钩子

- **书面化钩子**：让对方在 ticket comment 里写明“Testing 是统计口径，不代表生产无风险”。
- **责任归位钩子**：谁改字段 / 谁主张统计口径，谁给判断依据。
- **风险接受钩子**：如果判断生产不受影响，要求给依据；如果依据不足，保留 open risk。
- **权限 owner 钩子**：生产权限在哪一方，执行 owner 就不能默认落到无权限方。

---

## 7. 禁忌

- 不翻旧账说“你们一直偏袒 QA”。
- 不在第一轮让 Boss 裁判人，只让 Boss 裁判流程口径。
- 不说“你在降级风险”，说“避免统计口径和风险范围混淆”。
- 不承诺“业务研发整理清单 / 完成验证 / 负责升级闭环”，只承诺“对具体技术点做确认”。
