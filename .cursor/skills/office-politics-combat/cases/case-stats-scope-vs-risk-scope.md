# Case: 统计口径 vs 风险影响范围（白手套降级风险）

本案例处理的"形状"是：**对方把一个具有真实业务 / 合规 / 安全影响的风险，改写成某个统计项 / 归类项 / 环境字段，从而实质性降级风险**。

> 本案例为**复合示例**：方法论结构来自跨团队风险治理的常见模式，对话样本由作者改写虚构，
> 不对应任何具体公司、人物、工单或事件。文中所有角色名（Me / Boss / QA_Gatekeeper 等）
> 均为通用代称，可替换为读者自己环境中的对应角色。如读者在阅读时联想到具体某人或某事件，
> 纯属议题本身的普遍性，不构成对任何真实主体的指涉。

---

## 0. 适用场景（不止 IT 行业）

这个案例的核心矛盾是"统计口径"和"实际风险范围"被故意混为一谈。它在多个行业都成立：

| 行业 | 具体形态 |
|------|---------|
| 互联网 / 安全 | 审批 / 审计风险被归类成"非主环境""统计不计入项目" |
| 银行 / 风控 | 操作风险被归到"系统调试事件"分类，不计入合规口径 |
| 制造 / 品控 | 工艺缺陷被归到"试制阶段记录"，不计入正式品质统计 |
| 政府 / 国企 | 投诉被归到"非业务投诉"，不计入KPI |
| 学术 / 临床 | 不利结果被归到"探索性数据"，不计入主分析 |

读案例时把具体名词换成你所在行业的等价物即可。

## 1. 输入（用户提供，已脱敏）

```text
【我是谁】Me，业务研发
【对方是谁】
  - QA_Gatekeeper：相邻团队负责人，掌握部分流程口径与归类裁定权
  - Boss：我的直属老板，历史上偏袒 QA_Gatekeeper
【渠道】工单系统 + 工作群
【议题概述】
  - 流程 A 存在身份可信度 / 审计可信度风险
  - 我把这个风险作为一项 issue 提出
  - QA_Gatekeeper 主张：这条 issue 按统计规则归到"非业务环境"分类，不影响业务团队统计
  - 但议题真实涉及的是某个核心链路的审计风险，不是统计字段归属问题
【附加张力】
  - 业务团队的某项操作权限已收回到对方一侧
  - 对方在权限收回的同时，又试图把执行责任 @ 回无权限的业务团队
【我的诉求】
  1. 不接没有权限的执行 owner
  2. 不让风险范围被改写成统计项
  3. 必要时让 Boss 拍流程口径，而不是裁判 QA 对错
```

---

## 2. 局势判断

这是典型的**换框 + 降级风险**：

- 原议题：流程 A 是否存在风险，谁有权限谁执行，风险范围如何记录
- 对方换框：这只是某统计字段下的归类问题，不影响业务团队的项目统计

不要争"统计归属"，要把议题拆成两个独立字段：

1. **统计口径**：是否计入某项目 / 某环境 / 某报表
2. **风险影响范围**：是否影响真实链路、审计可信度、权限边界、历史记录

---

## 3. 对方动作识别

| 对方话术 | 动作 | 真实效果 |
|----------|------|----------|
| "不能影响项目统计" | KPI / 指标防御 | 把风险变成统计争议 |
| "按规则统一归到某非主分类" | 规则挡箭 | 用归类规则覆盖真实风险范围 |
| "麻烦你方支持下" | 责任回推 | 在权限被收回后，把执行责任推回无权限方 |

---

## 4. 我方原则

- 接受统计口径，不接受用统计口径替代风险范围。
- 接受技术确认，不接受无权限的执行 owner。
- 如果 Boss 偏袒 QA_Gatekeeper，不要直接 @ Boss 裁判"QA 对不对"；只让 Boss 确认流程口径 / 风险记录规则。

---

## 5. 推荐回复

### 对 QA_Gatekeeper

> 理解，不影响业务团队项目统计这点我没有异议。如果按规则统一归到某非主分类，也可以按这个统计口径处理。
> 
> 我这里想确认的是另一个维度：这条 issue 的风险影响范围。这个问题描述的是核心审批链路里的身份来源和审计可信度，不是某分类字段下的页面或参数问题。
> 
> 如果环境字段的归类只是统计口径，麻烦在 ticket comment 里明确一下：该字段用于统计，不代表核心链路无风险。
> 
> 如果对方确认核心链路不受影响，也麻烦补一下判断依据，避免后续复盘 / 审计时，把"统计口径"误解成"风险影响范围"。

### 如果对方继续说"按规则都归到某非主分类"

> 明白，这是统计规则。我这里确认的是风险影响范围，不是统计规则。那我理解为：环境字段按统计规则归到某非主分类，但该 issue 是否影响核心审批链路还需要对方一侧单独确认，对吗？

### 如果对方说"已经 Done / 已修复"

> Done 我理解是修复状态；我这里确认的是影响范围判断依据。修复完成不等于该风险只存在于某非主分类。麻烦补一下核心链路不受影响的依据，我这边按结论记录。

---

## 6. 是否 @ Boss

### 默认不要第一时间 @ Boss

如果 Boss 历史上偏袒 QA_Gatekeeper，直接 @ Boss 很容易变成给 QA 借权威压人的机会。先在 ticket / 群里钉住一句：

> 统计口径可以按对方主张的归类处理，但风险影响范围需要单独确认。

### 何时 @ Boss

满足任一条件再 @：

- 对方持续把统计口径当作风险范围，不愿在 ticket 里拆开说明。
- 对方把无权限执行责任推给业务研发。
- 风险已影响多个团队或链路。
- 24 小时内没有明确 owner / 判断依据。

### @ Boss 的正确问法

不要问：

> QA 这样改对不对？

要问：

> @Boss 我想同步确认一个流程口径，避免后续大家理解不一致。
> 
> QA_Gatekeeper 提到这条 issue 按统计规则归到某非主分类，不影响业务团队项目统计。这个统计口径我没有异议。
> 
> 但这条 issue 描述的是核心审批链路的身份来源和审计可信度，可能涉及核心治理风险。所以这里想请你帮忙拍一下：
> 
> 1. 环境字段的归类是否仅代表统计口径；
> 2. 是否仍需要对方一侧单独确认核心审批链路是否受影响；
> 3. 如果风险范围未确认，是否应该在 ticket comment 里保留说明，避免后续审计 / 复盘误解。
> 
> 我只是希望把统计口径和风险影响范围拆清楚，避免后续责任边界不清。

---

## 7. 钩子

- **书面化钩子**：让对方在 ticket comment 里写明"该归类只是统计口径，不代表核心链路无风险"。
- **责任归位钩子**：谁改字段 / 谁主张统计口径，谁给判断依据。
- **风险接受钩子**：如果判断核心链路不受影响，要求给依据；如果依据不足，保留 open risk。
- **权限 owner 钩子**：操作权限在哪一方，执行 owner 就不能默认落到无权限方。

---

## 8. 禁忌

- 不翻旧账说"你们一直偏袒某一方"。
- 不在第一轮让 Boss 裁判人，只让 Boss 裁判流程口径。
- 不说"你在降级风险"，说"避免统计口径和风险范围混淆"。
- 不承诺"业务团队整理清单 / 完成验证 / 负责升级闭环"，只承诺"对具体技术点做确认"。
